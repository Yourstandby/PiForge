# Token 消耗审计（最近 7 天真实会话）

> 只审计，不改机制。数据来源：`~/.pi/agent/sessions/**/*.jsonl` 里
> `type: "message"` 的 assistant 条目（`message.usage`），脚本：
> `scripts/audit-token-usage.mjs`（`--days` / `--idle-gap` / `--json`）。
> 前缀机制（`prompt-prefix.ts`）、工具域、`smoke:prefix-budget` **一行未动**。

## 0. 口径与一个必须说明的偏差

```bash
node scripts/audit-token-usage.mjs            # 默认 7 天 / 空闲阈值 10 分钟
node scripts/audit-token-usage.mjs --days 14 --json
```

- 采样：**60 个会话文件 / 10 227 次模型调用**，其中 **57 个会话在 `--D--Pi-PiForge--`**
  （也就是"用 PiForge 开发 PiForge"的场景，含大量 subagent / orchestrator 运行）。
  因此下面的绝对值偏"重度 agentic 使用"，结论方向可用，量级别直接当普通用户数据。
- `cacheWrite` 全程为 0（该 provider 的 usage 不上报写入侧），所以"前缀失效"用
  **cacheRead 骤降 + 未命中 input 变大** 来识别，不用 cacheWrite。

## 1. 总量与成本结构（这是本轮最重要的发现）

| 指标 | 值 |
|---|---|
| 总 tokens | 2 070 480 052（≈2.07 B） |
| 其中 cacheRead | 2 055 030 528（**99.3%**） |
| 未命中 input | 9 821 680（0.47%） |
| output | 5 627 844（其中 **reasoning 2 539 197 = 45%**） |
| 总花费（provider 上报） | **$22.36** |
| 实测单价（由 cost/tokens 反推） | input `$3.08e-7` · output `$1.21e-6` · cacheRead `$6.09e-9` |

**成本拆解**：`cacheRead 56% ($12.51)` · `output 31% ($6.83)` · `input 14% ($3.02)`

推论：`input/cacheRead ≈ 50×`、`output/cacheRead ≈ 200×`。

- **最大成本项是"每次调用都要重读的上下文"（cacheRead 56%）**，不是缓存失效。
  每次调用 cacheRead 中位 **142 976 tok**、p90 **471 168**、max **717 056**。
- 8 个最贵的会话吃掉 $14.67 / $22.36（66%），它们的 `avgCtx` 在 237k–379k tok/次。

## 2. (a) 空闲恢复重发：44 次，750k tok，$0.22（占 1%）

阈值：距上一次请求 ≥10 分钟。

| 时间 | 间隔 | 未命中 input | 上一条 cacheRead |
|---|---|---|---|
| 2026-10-23T05:17Z | 14 min | 267 915 | 270 720 |
| 2026-10-19T10:39Z | 40 min | 179 163 | 178 304 |
| 2026-10-22T06:38Z | 834 min | 91 270 | 90 368 |

- 合计 749 924 tok，占全部未命中 input 的 **7.6%**，占总额 **0.036%**；
- 间隔中位 **26 分钟** —— 说明 10 分钟阈值下大部分空闲期缓存仍有效（`cache-warming: idle`
  在起作用），真正"凉透"的只有极少数。

**结论**：P2-3（按成本决定"预热 or 提示"）**优先级应下调**。它最多省 ~$0.2/7 天，
而误判（该预热没预热）会带来额外往返。建议：只做"**预估重发 ≥ 阈值时提示用户**"
这一半（纯提示，零风险），不做自动预热决策。

## 3. (b) 前缀失效：35 次，3.65M tok，$1.12（占 5%）

识别规则：上一条 cacheRead ≥20k，这一条 cacheRead < 上一条的 10%，且未命中 input ≥10k。

| 时间 | cacheRead 变化 | 重发 input |
|---|---|---|
| 2026-10-19T14:52Z | 322 304 → 0 | **323 535** |
| 2026-10-19T14:54Z | 324 352 → 3 200 | **321 023** |
| 2026-10-21T15:23Z | 314 624 → 0 | 319 634 |
| 2026-10-23T05:17Z | 270 720 → 4 096 | 267 915 |

- 合计 3 645 022 tok（≈全部未命中 input 的 **37%**），花费 $1.12 ≈ 总额 **5%**；
- 前两条相隔 2 分钟、同属一个会话、各重发 ~320k —— 这种"连续两次整段重发"最像
  **跨 app 切换 / Host 重启 / 工具集变化**（JSONL 里没有 app 标识，无法进一步归因，
  这正是 P2-2 要补的信息）。

**结论**：P2-2（跨 app / 跨工具集切换检测）值得做，但定位应是**护栏而不是省钱**：
35 次/7 天的量级，省下的钱有限；价值在于"让用户看见 40 万 token 的重发并建议开新会话"。

## 4. (c) output 分布：31% 成本，中位 291 tok/次

| 任务类型（按工具粗略分类） | 调用数 | output 合计 | 占比 | 每次均值 |
|---|---|---|---|---|
| 跑命令（shell/bash） | 8 057 | 3 649 243 | **65%** | 453 |
| 改代码（edit/write） | 1 197 | 1 540 976 | 27% | **1 287** |
| 纯回答（无工具） | 392 | 295 362 | 5% | 753 |
| 只读探查（read/grep） | 455 | 110 800 | 2% | 244 |
| 其余（codemode/browser/…） | ~130 | 约 29k | <1% | — |

- 每次调用 output 中位 **291**、均值 **550** —— 与基线"PiForge 668 tok/call"同量级
  （本次样本含 subagent，均值被拉低）；
- **reasoning 占 output 的 45%**（2.54M / 5.63M）：思考 token 按 output 计价，
  这是"看起来 output 高"的主要来源，而不是"答复啰嗦"；
- shell 类调用 8 057 次（79% 的调用）平均 453 tok —— 每次工具调用都要输出一段
  "我要做什么"的叙述，这是可以约束的地方。

**结论**：output 侧 PiForge 已经优于 PAD（668 vs 1 140 tok/call），**不建议**再压
"答复长度"（收益小、体验损失大）。真正可做的是"**少叙述、多并行工具调用**"
（引导模型把多步探查合成一次），属于工具/prompt 层的既有能力，不需要新机制。

## 5. 候选干预点：哪些"不改前缀机制"

| 干预 | 类型 | 预期收益（按本机 7 天） | 是否动 prompt-prefix | 建议 |
|---|---|---|---|---|
| **P2-2 跨 app / 跨工具集切换提示** | 纯提示层（读 `prefixAudit`，弹可关闭提示） | 直接省钱 $0–1.1（取决于用户是否改开新会话）；**主要价值是可见性** | ❌ 不动 | ✅ 做（护栏） |
| **P2-3a 恢复成本提示**（预估 ≥阈值才提示） | 纯提示层 | ≤$0.2 | ❌ 不动 | ✅ 做（只做提示那一半） |
| P2-3b 自动预热 | 需要新增一次请求 | 可能为负（误判时多付一次） | ❌ 不动 | ⏸ 不做 |
| **上下文规模治理（压缩策略）** | 动 `desktop-compaction-extension`（不是 prompt-prefix） | **潜在最大**：cacheRead 中位 143k → 若降到 ~90k，≈ −$3/7d（−14%） | ❌ 不动（压缩只改历史消息，前缀快照仍可审计） | 🔎 下一轮立项（需单独评审，因为它改行为） |
| **工具调用合并引导**（减少"叙述 + 单步"） | 工具层既有能力（并行调用 / 批量提示） | output 侧 5–10% | ❌ 不动 | 🔎 观察 |
| 全按需域（shell+memory+orchestrator） | 动工具域 | −648 tok/轮，但 break-even ≈31 轮 | ✅ **会动**（已评估：默认关闭） | ❌ 维持默认关闭 |

**明确写死**：本轮与下一轮允许做的 P2-2 / P2-3a **只在提示层**，不触碰
`agent-host/prompt-prefix.ts`、`DOMAIN_TOOL_NAMES`、`smoke:prefix-budget`；
每次改动后仍以 `npm run smoke:prefix-budget`（当前 6 640 tok / 99.6%）为门禁。

## 6. 建议下一步

1. **进实施**：P2-2（跨 app/工具集切换提示）+ P2-3a（恢复成本提示）。
   两者都只读 `agent.state.prefixAudit` 与最近一次 `usage.input`，不改前缀生成。
2. **进立项（不实施）**：上下文规模治理（压缩触发点 / 会话拆分建议）。
   目标是把每调用 cacheRead 中位从 143k 压到 ≤100k；先做 A/B 量它是否影响
   任务成功率与输出质量。
3. **继续观察（不做）**：P2-3b 自动预热、全按需域默认开启、output 长度压缩。

### subagent 上下文（L-C）：上界 0.004%，且隔离机制本来就在

`npm run audit:subagent -- --days 365`（本机 60 会话 / 10 390 请求 / cacheRead 2.15B tok / $23.10）：

| 指标 | 实测 |
|---|---|
| 用过派发的会话 | **2 / 60（3.33%）**，共 **3 次**（`herdr_spawn` 1 / `orchestrator_spawn` 1 / `spawn_agent` 1） |
| 占全部工具调用 | **0.027%** |
| 有派发的父会话 cacheRead/调用 | **89 911**（低于无派发的 **214 187**）→ 派发与上下文膨胀**无相关性** |
| 子 Agent 成本上界 | 3 轮 × 10 000 tok = **30 000 tok/次**，合计 90 000 = 观测 cacheRead 的 **0.004%** ≈ 0.21 次父调用 |

代码事实（`agent-host/subagents.ts`）：子 Agent 用 `SessionManager.inMemory(cwd)`（不写 JSONL、
**不继承父 transcript**）、`noContextFiles: true`、独立 `childSystemPrompt`（固定文案实测 ≈71 tok），
外加三道硬闸门：3 轮上限 / 单轮 10k 熔断 / 回包 ≤1 200 字符。

**结论**：这条杠杆没有可省的 token（"隔离"已经在做），不立项。
方法论补充：子 Agent 不落盘，所以"从磁盘按 parentSessionId 聚合"这条路**不存在**
（`scripts/audit-token-usage.mjs` 头部也写了这条，避免下次重复找）。

### 压缩触发点前移（L-A）：预演未通过，已证伪

`docs/optimizations/l-a-preview-report.md`（24 次预演，8 道长上下文题 × C1/C2/C3 三档压缩）：

| 状态 | 通过 | 首轮上下文 | 整题上下文总量 | cacheRead 中位/调用 | 成本 |
|---|---|---|---|---|---|
| C1 现状（硬顶 48k） | **6/8** | 49 190 | 302 175 | 50 016 | $0.1481 |
| C2 前移 30%（硬顶 33.6k） | **4/8** | 48 445（−1.5%） | 450 814 | 49 696（−0.6%） | $0.1569 |
| C3 前移 50%（压力档） | **6/8** | 30 659（−38%） | 189 128（−37%） | 31 296（−37%） | $0.1027 |

关键点（三轮一致）：**能用阈值调出来的档位（C2）几乎没有收益还掉 2 题；
有收益的档位（C3）需要"轮内成对裁剪"，不是阈值能调出来的配置。**

两条结构性原因（不是调参能解决的）：
1. 真实请求的上下文 ≈ 前缀/工具/系统提示（约 18k）+ 保留历史。把历史从 33k 砍到 22k，
   落到整条请求上只是小头，模型还会自己读文件把量补回来；
2. 「整轮保留」是压缩的硬下限：本机最大的真实会话最后一轮本身就有 ~22.6k tok，
   压到 12k 已属于"拆轮内结构"的压力档。真实场景里"压缩后仍剩 20k+"是常态。

> 与 L-D 的区别：L-D 是"没东西可省"，L-A 是"省得到的那一档会掉质量"。
> 两条都做过实测，token 线到此关闭。
