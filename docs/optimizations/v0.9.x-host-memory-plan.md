# Step 4 立项：agent-host ≤220 MB 的可行路径

> 目标：host RSS **304 MB → ≤220 MB**（−84 MB）。
> 本文只做立项：给证据、拆解、候选杠杆、回归清单，不改运行时代码。
> 数据来源：`scripts/audit-route-heap.mjs`、`scripts/audit-route-deps.mjs`、
> `PIFORGE_DEBUG_HOST_CPU=1`、`npm run measure:packaged`。

## 1. 先纠正一个错误假设：路由常驻**不是**主要开销

`audit-route-heap` 给每条路由做"GET 一次 → 强制 GC → 读 Host heapUsed"，
70 条路由全部走完，累计 heap 只从 ~36 MB 涨到 ~42 MB：

| 路由（按首载 heap 增量） | heap 增量 | 累计 heap | 静态依赖字节 |
|---|---|---|---|
| `/api/auth/all-providers` | **2 586 KB** | 39.7 MB | 58 KB |
| `/api/upstream/versions` | 726 KB | 41.2 MB | 12 KB |
| `/api/auth/login/[provider]` | 282 KB | 36.7 MB | 20 KB |
| `/api/sessions/[id]/branches` | 268 KB | 36.8 MB | 81 KB |
| `/api/models` | 266 KB | 42.2 MB | 30 KB |

- 所有 70 条路由的**正增量合计 ≈ 6.2 MB**；
- 静态依赖图里最大的路由也只有 85 KB 自有代码；
- 结论：**"把扫描型路由改成懒加载"最多省个位数 MB**。上一轮已经懒加载过了，
  再优化没有意义。

## 2. 304 MB 到底由什么组成（实测拆解）

`PIFORGE_DEBUG_HOST_CPU=1`（打包版空闲，已加载一个会话）：

```
[host-cpu] 0.00% over=1006ms rss=304MB heapUsed=93MB heapTotal=143MB external=9MB arrayBuffers=0MB
```

单独起 Host（`node agent-host/dist/agent-host/index.js`，**未加载任何路由**）：

```
启动后（无 worker 时）host RSS = 329 MB
第一次 git status（拉起常驻 worker）后 RSS = 343 MB   → 每个 worker 线程 ≈ +14 MB
第二次 git status（复用 worker）后 RSS = 344 MB
```

| 组成 | 大小 | 说明 |
|---|---|---|
| `heapUsed` | 93 MB | JS 活对象；其中路由层只占 ~6 MB，其余是 Pi SDK + 会话状态 |
| `heapTotal − heapUsed` | 50 MB | V8 预留的 GC 余量（新生代/老生代空转空间） |
| `external + arrayBuffers` | 9 MB | Buffer / TypedArray 等 |
| **其余（RSS − heapTotal − external）** | **≈152 MB** | V8 code space、JIT、40 MB 已加载模块的编译产物、ICU、native addon、线程栈（每线程 ~1 MB + isolate）、sqlite mmap、Electron/Node 运行时 |
| 常驻 worker 线程 | 14 MB/个 | 目前后台有 1 个常驻 git worker |

**所以：84 MB 的缺口只能从"native 侧 + V8 余量 + 线程"里找，不能从"路由模块"里找。**

## 3. 候选杠杆（按预期收益/风险排序，均需实测确认）

| # | 杠杆 | 预期收益 | 风险 | 验证方式 |
|---|---|---|---|---|
| L1 | **V8 堆余量收敛**：`--max-old-space-size=192`、`--max-semi-space-size=8`（当前 heapTotal 143 vs used 93） | 10–30 MB | 中（堆积过多会 OOM；需要长会话压测） | `measure:packaged` + `measure:long-session` 30 轮不 OOM |
| L2 | **git worker 空闲回收**：空闲 60 s 后 `worker.terminate()`，下次扫描再拉起 | 14 MB | 低（下次扫描多付 100–150 ms 启动税） | `audit-route-heap` 前后 RSS 对比 |
| L3 | **Pi SDK 子系统懒加载**：LTM sqlite、orchestrator、fleet、browser bridge 在首次使用时才 `import()` | 20–40 MB（待测） | 中高（会改变"工具注册时机"，必须守住前缀稳定性：`smoke:prefix-budget`） | `--cpu-prof` 模块耗时 + `heapUsed` 分解 |
| L4 | **会话/上下文驻留上限**：每个打开会话的 transcript 常驻 heap；把非活动会话的 `messages` 降到"仅元数据 + 按需回读" | 10–30 MB（取决于打开几个会话） | 中（切会话可能多一次磁盘读） | 打开 1/3/5 个会话分别测 RSS |
| L5 | **native 侧定位**：`process.report.getReport()` / `vmmap` 找那 152 MB 的真实归属（ICU？sqlite mmap？JIT code？） | 未知，可能 0 | 低（只读诊断） | 输出 `docs/optimizations/host-native-memory.json` |
| L6 | 常驻 worker 改为 `--max-old-space-size=64` | 5–10 MB | 低 | 同上 |

建议顺序：**L5（4 小时定位）→ L2（半天，低风险确定性收益）→ L1（1 天，需压测）→ L3/L4（各 2 天，需回归）**。

> 如果 L5 显示那 152 MB 主要是 V8 code space / Electron 运行时（不可压缩），
> 那么 220 MB 这个目标本身需要复议：**Pi SDK 的 JS 依赖图就决定了 ~200 MB 的下限**，
> 参考 PAD 的 183 MB 也是同一量级。届时建议把验收线改为 **≤250 MB** 并记录依据。

## 4. 三条主链路的回归清单（任何 L1–L6 改动都必须过）

### 4.1 会话链路
- [ ] 新建会话 → 发一条消息 → 流式输出正常结束（`agent_end` 不丢）
- [ ] 切换会话 3 次：transcript/滚动位置/输入框草稿不串
- [ ] fork / branch / clone / export 各 1 次
- [ ] 长会话 30 轮：`npm run measure:long-session`（命中率 ≥90%、无 OOM）
- [ ] 压缩（结构化压缩）1 次，压缩后仍能继续对话

### 4.2 文件链路
- [ ] 文件树展开 3 层；打开 2000 行 `.ts`（高亮正常）
- [ ] 编辑并保存（`/api/files/apply`）→ Git 面板标记刷新（`refreshKey` 通道）
- [ ] 拖拽上传 1 个图片（32 MB 上限内）+ 预览
- [ ] Git：status / diff / commit 各 1 次；`/api/git/status` 在 3 s 内重复请求命中缓存
- [ ] 文件授权拒绝路径：访问 `~/` 之外返回 403

### 4.3 模型链路
- [ ] 模型列表加载（含扩展模型）；切换模型后首条消息正常
- [ ] 辅助模型（image/decision）配置后工具出现；未配置时不出现
- [ ] `/api/usage/upstream` 与上下文环数值合理
- [ ] **前缀不变量**：`npm run smoke:prefix-budget` exit 0（6 640 tok / 命中 ≥90%）
