## 0. 一句话结论

启动、内存、CPU、GPU 四项都已进入"达标"或"已归因不可动"；剩下唯一的边界
（host 加载 26 MB 大会话时 ~286 MB）已被证明是**上下文数据本身**的代价，不是浪费。
**运行效率线关闭。**

## 2. 已归因、不可动（再做也是这个数）

| 项 | 归因 | 为什么不继续动 |
|---|---|---|
| **GPU 155 MB** 达不到 150 | 这台机器 `gpu_compositing: disabled_software`、`opengl: disabled_off`（远程会话/blocklist），硬件加速不可用 | 4 种开关组合都落在 155 MB；`--in-process-gpu` 实测 main 涨到 373 MB、总内存更差且崩溃半径变大；且 **150 的门槛低于对标 PAD 自己的 152 MB** |
| **Host 峰值 252.9 MB / 大会话 286 MB** | 26 MB 真实会话的 transcript 本身就要加载进来；heapUsed 93 + heapTotal 余量 50 + external 9 + native ~152（见 `host-memory-review.md` 的分解） | 这是"用户数据本身的代价"；唯一还能动的是 native 部分，属运行时改造 |
| **`--max-rss-mb 220` 永远不过** | 该参数是**整个 App 总 RSS**（850–1130 MB），不是 host | 口径错误，不是性能问题；host 门禁是 `--max-host-rss-mb`（见 §4） |
| **路由懒加载不是 host 内存杠杆** | 70 个 API 路由全量 heap ≈ **6.2 MB** | 收益 <1%，不值得引入懒加载复杂度（`docs/optimizations/route-heap.json`） |
| **utility 传输层 285 MB** | `utilityProcess.execArgv` 只能带一个 `--js-flags`，新生代设不下去 | 已切成 node 传输层；utility 只作回退（门禁 290） |

## 3. 已证伪（做过实测，结论是不做）

| 项 | 当时的假设 | 实测结论 |
|---|---|---|
| **host ≤220 MB 作为通用目标** | 220 是合理稳态线 | 只在轻载成立（193–221 MB，7 次里 4 次过）；加载 26 MB 会话时两种传输层都是 ~286 MB。**稳态门禁改为 240**（§4） |
| **node 传输层"−150 MB"** | 探针 116 MB vs utility 265.6 MB | 口径错误：116 MB 是**裸 host**，265.6 MB 是加载了 API 桥+会话索引的 host。同口径真实收益：**中位 268.4 → 209.1 MB（−22%）**，最坏尖峰 **349.4 → 296.6 MB** |
| 一次性"关掉 GPU 进程" | 省 228 MB | `--in-process-gpu` 总内存反而更高（891.8 MB），已否决 |
| 每轮全量重算 git 快照 | — | 已改为 3 s TTL + single-flight + 常驻 worker（`step3-idle-cpu.md`） |

## 5. 关闭后的观察义务（不是任务，是报警条件）

1. `measure-packaged` 的 host RSS 中位连续 3 次 > 240 MB → 查是否有新的常驻缓存；
2. soak 出现 OOM（`<userData>/host-oom.json` 非空）→ 回退顺序：
   `PIFORGE_HOST_HEAP=default` → `PIFORGE_HOST_TRANSPORT=utility`；
3. 空闲 CPU >3% → 先看 `PIFORGE_DEBUG_HOST_CPU=1` 的 `[host-cpu]` 行（含 GC 统计）；
4. GPU 高于 200 MB → 看 `gpu-evidence.json` 的 `decision.code` 是否变了。

## 6. 与 token 线的关系

两条线互不重叠：**运行效率线管"进程占多少内存/CPU"，token 线管"模型调用花多少钱"**。
本轮把两条线都关掉了，理由不同：

- 运行效率线：**指标已达标或已归因**，继续投入没有可测收益；
- token 线：**两条候选被实测证伪**（L-D、L-A），第三条依赖真实用户数据 —— 见
  `docs/optimizations/token-line-closure.md`。

唯一共享的教训写在 `docs/optimizations/preview-harness-pitfalls.md`：
**"数字看起来对、其实量错对象"是这两条线最常见的失败模式**（进程聚合、中位 vs 峰值、
续跑用量、路径泄漏都属于这一类）。
