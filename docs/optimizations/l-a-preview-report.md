# L-A 预演报告：把压缩触发点前移，模型还能答对吗？

> **口径提醒（先读这段）**：本报告是**预演**，24 次调用（8 题 × 3 状态，每格只跑 1 次）。
> 它只能判断**方向**，不足以下显著结论 —— 单元里的通过/失败会受模型随机性影响（本报告里
> `E4` 在 C1/C3 通过、C2 失败，就是非单调的噪声）。正式结论必须走 A/B（每格 ≥20 次）。
> 本轮的用途只有一个：**决定要不要为 L-A 立项**。

- 日期：2026-10-24
- 素材：本机最大的真实会话（26.0 MB，1486 条 entry，77 轮，已发生过 10 次压缩）
- 判分集：`scripts/ab-context-tasks.json` 里 8 道长上下文题
  （E2 / E3 / E4 / E5 / T3 / S1 / S2 / S5）
- 单次成本：24 次约 **$0.4/轮**，用时 **12–15 分钟**；共跑 **3 轮**（第 1、2 轮暴露了路径泄漏 bug，第 3 轮修好后复现同一结论）
- 归档：`docs/optimizations/l-a-preview/{C1,C2,C3}-summary.md` + `states.json`
  （完整状态会话在系统临时目录，**不写** `~/.pi/agent/sessions`，避免污染 `audit:token` 口径）

## 1. 三种状态怎么构造的

阈值取自 `agent-host/compaction-plan.ts` 的真实常量（硬顶 `MAX_CONTEXT_TOKENS = 48_000`、
预算比 `CONTEXT_BUDGET_RATIO = 0.45`），只改触发点，不改机制：

| 状态 | 触发点 | 硬顶 | 预算比 | 保留（尾部整轮） | 摘要 | 估算上下文 |
|---|---|---|---|---|---|---|
| **C1** | 现状 | 48 000 | 0.45 | 152 条 ≈ 33 654 tok | 1 226 tok | 41 520 tok |
| **C2** | 前移 30% | 33 600 | 0.315 | 102 条 ≈ 22 641 tok | 1 234 tok | 30 515 tok |
| **C3** | 前移 50% | 24 000 | 0.225 | 55 条 ≈ 11 950 tok | 1 234 tok | 19 824 tok |

构造方式：按整轮（user 消息为界）从会话尾部保留，直到达到目标 token；被丢弃区间用
**确定性四段式摘要**（用户意图 / 涉及文件 / 关键报错 / 最终决策）替代。

> 摘要不是模型写的 —— 这是**刻意保守**：确定性抽取只会丢信息，不会"编"。如果模型在
> 这种更差的摘要下仍能答对，真实（模型）摘要应当更好。

C3 触到一个硬约束：**单轮体量决定压缩下限**。这轮真实会话的最后一轮本身就 ≈22.6k tok，
按"整轮保留"根本压不到 12k，所以 C3 额外做了**成对裁剪**（保留一个 assistant 消息 +
它触发的 toolResult 作为不可分单元，从尾部往前留，仍超长才按现有 4 000 字符预算截断输出）。
这也解释了为什么真实场景里"压缩后仍剩 20k+"是常态。

| 判据（预演级） | 目标 | 实测 | 结果 |

## 4. 为什么不通过（比"错了几题"更重要的两条）

**（1）低压缩没有收益，高压缩才有效果，而效果档掉题。**

- C2 的保留历史少了 27%（33.6k → 22.6k tok），但**首轮真实上下文只降了 1.5%**，
  cacheRead 中位只降 0.6%（三轮分别是 −2.1% / −2.5% / −0.6%，同一量级）。
  原因：真实请求里上下文 = 前缀/工具/系统提示（约 18k） + 保留历史；把历史从 33k 砍到
  22k，落到整条请求上只是个小头，而且模型自己还会读文件把量补回来。
- 唯一"看得见"的档位是 C3（压力档：在轮内成对裁剪）：首轮上下文 −38%、
  整题上下文 −37%、成本 −31%。它**没有**掉题（6/8，与 C1 持平），
  但 C3 已经不是"调阈值"能得到的配置（见 §1 的说明）。
- 也就是说：**能用阈值调出来的档位（C2）几乎没有收益，有收益的档位（C3）阈值调不出来**。
  token 线继续投入的唯一杠杆（模型侧 / 工作流改造）已经超出"调参"范畴。

**（2）长上下文题在这套判分集里对压缩不敏感，因为它们能自己读文件。**

8 题里 4 题（S1 / S2 / S5 / T3）在三种状态下表现完全一致 —— 它们需要的信息在**仓库里**，
模型不依赖会话历史就能重新读到。真正受影响的是 E 类（改代码位置类）：
历史里"之前讨论过这个文件"的上下文被压掉后，定位成本上升，偶尔就做错了。
这提示 L-A 的真实风险不在"记不住结论"，而在"**定位漂移**"。

## 5. 本次踩到并已修掉的两个坑（会影响任何后续预演/实验）

1. **历史里的绝对路径会把改动写进真实仓库**：transcript 里到处是 `D:\Pi\PiForge\...`，
   模型照着历史路径改文件，于是第一版预演把 `electron/host-heap.ts` 改在真实仓库里、
   根目录还多出 `ab-answer.json`，而工作树里的判据全红。
   现在 `runTask({ rewriteRepoPaths: true })` 会把状态文件里的仓库路径改写到本次工作树，
   并在过程里核对 `git status` 保持干净。
2. **不能按消息随手切会话**：pi 装载会话时 toolCall / toolResult 成对消费，
   中间插一条合成消息或丢掉一条 result，`agent.ensure` 之后的 prompt 会**完全不起作用**
   （实测 C3 第一次跑出来 `calls=0`，看起来像"模型拒绝回答"）。
   现在裁剪的最小单位是"一个 assistant 消息 + 它触发的 toolResult"。

另外修了度量口径：续跑会话里已有历史，`readUsage` 必须**只统计本次 run 新增的行**，
否则历史里几万 token 的 cacheRead 会被算进"这一题的成本"（第一版报出来的 81 次调用就是这么来的）。

## 6. 对 token 线的处置

| 杠杆 | 状态 |
|---|---|
| L-D 工具输出 4 000→2 000 | **已证伪**（80 次 A/B：cacheRead −0.4%、成本 +1.4%、耗时 +17.8%） |
| L-A 压缩触发点前移 30% / 50% | **已证伪（预演级，三轮）**：C2 掉 2 题且上下文只降 1.5%；C3 有效但需要拆轮内结构 |
| L-B 会话拆分提示 | 降级待真实用户数据（提示层，与 token 机制无关） |

**token 线到此关闭**：三条候选要么被实测证伪，要么依赖真实用户行为数据。
后续若还要动，只剩两个方向，且都超出"调阈值"的范畴：
① 模型侧（换更便宜/更长上下文的模型）；② 产品侧（会话切分的工作流改造，属 UX 而非 token 工程）。

## 7. 三轮之间修掉的 bug（已并入工具，避免下次重复踩）

1. **历史绝对路径泄漏到真实仓库**（第 1、2 轮）：模型照抄 transcript 里的
   `D:\Pi\PiForge\...` 改文件，改动落到真实仓库、工作树判据全红。
   修法：在 **JSON 层面**递归替换字符串值（文本替换会漏掉转义形态 `D:\Pi\PiForge`），
   并加**跑后护栏**：每轮 `git status --porcelain` 检查 tracked 修改，命中就只回滚那几个文件
   并给该次 run 打 `leakedRepo` 标（第 3 轮抓到 5 次，均已回滚）。
2. **共用一份改写后的状态文件**：`-rw.jsonl` 名字固定 → 上一轮的历史累积到下一轮，
   后面的 run 会看到"已经做完了"。修法：每次 run 用独立文件。
3. **`readUsage` 统计了历史用量**：续跑会话里已有几百条 assistant 消息，
   第一版把历史 cacheRead 全算进"这一题的成本"（报出 81 次调用）。
   修法：只统计本次 run 新增的行。
4. **`isStreaming` 判定过早退出**：刚发 prompt 时它还是 false，循环立刻退出 → 记成 `calls=0`。
   修法：必须**先看到本次 run 新增的 assistant 消息**，再等 stats 稳定。
5. **轮内裁剪必须成对**：按消息随手切会让 `agent.ensure` 之后的 prompt 完全不起作用。
   最小裁剪单元 =「一个 assistant 消息 + 它触发的 toolResult」。
