# token 线收口：为什么关闭、关掉了什么、什么条件下重启

> 状态：**关闭**（2026-10-24）。本文是 token 优化这条线的**唯一收口结论**，
> 与 `docs/optimizations/token-consumption-audit.md`（审计原始数据）、
> `docs/optimizations/context-governance-plan.md`（候选清单）、
> `docs/optimizations/l-a-preview-report.md`（L-A 预演）互为引用。
> 运行效率线的收口见 `docs/optimizations/v0.9.x-performance-final.md`；
> 预演工具踩过的坑见 `docs/optimizations/preview-harness-pitfalls.md`。

## 0. 一句话结论

**token 成本的大头是"模型答对这道题所需上下文的固有成本"，不是我们能调掉的浪费。**
三条候选里两条已用实测证伪（L-D、L-A），第三条（L-B）依赖真实用户行为数据、不占工程预算。
**token 线关闭，默认值一律不动**（工具输出预算 4 000 字符、压缩硬顶 48 000 / 预算比 0.45 全部保持原样）。

## 1. 成本结构（审计实测，60 会话 / 10 227 次调用）

| 项 | 实测 |
|---|---|
| 总花费（provider 上报） | **$22.36** |
| cacheRead 占 token 量 | 2 055 030 528 tok（**99.3%**） |
| 成本拆解 | **cacheRead 56%（$12.51）** · output 31%（$6.83） · input 14%（$3.02） |
| 每次调用 cacheRead | 中位 **142 976** / p90 **471 168** / max 717 056 |
| 最贵的 8 个会话 | 吃掉 $14.67 / $22.36（**66%**），其 avgCtx 237k–379k tok/次 |

**结论**：成本 = 上下文规模 × 调用次数。所以"省 token"只有两条路：少读（缩上下文）、少调（少循环）。
下面每一条候选都在这两条路上被试过。

## 2. 已证伪清单（全部带实测数字）

| 候选 | 假设 | 实测 | 结论 |
|---|---|---|---|
| **空闲恢复重发** | 恢复会话要重发全部历史，值得优化 | 44 次 / 750k tok / **$0.22（1%）** | 占比太小，**证伪**（只保留可见性提示） |
| **跨 app 前缀失效** | 共用一个 `~/.pi/agent` 导致前缀失效 | 35 次 / 3.65M tok / **$1.12（5%）** | 占比小，**证伪**（只保留提示，不改前缀机制） |
| **subagent 上下文隔离（L-C）** | 子 Agent 继承父上下文 → 重复重读 | 3 次派发 / 2 会话（3.33%）/ 占工具调用 **0.027%**；成本上界 **0.004%**；且隔离机制本来就有（`SessionManager.inMemory` + 独立 system prompt + 3 轮/10k 熔断） | **不立项** |
| **工具输出阈值 4 000→2 000（L-D）** | 少读工具输出能省钱 | 80 次 A/B（2 轮 × 2 臂 × 20 题）：cacheRead 中位 9 024 → 8 992（**−0.4%**）、成本 $0.1688 → $0.1712（**+1.4%**）、耗时 13s → 15s（**+17.8%**）、成功率 85.0% → 82.5% | **证伪，不采纳** |
| **压缩触发点前移 30%（L-A C2）** | 压得更勤 → 每轮重读更少 | 24 次预演 × 3 轮：C1 **6/8**（首轮上下文 49 190）→ C2 **4/8**（48 445，**−1.5%**）；C2 的 cacheRead 中位只降 **−0.6%**；三轮一致（C1 6/5/6、C2 4/3/4） | **证伪，不采纳** |
| **压缩触发点前移 50%（L-A C3，压力档）** | 更激进会看到拐点 | 首轮上下文 −38%、成本 −31%，通过数 6/8（不掉题），但需要"轮内成对裁剪" —— **不是阈值能调出来的配置** | 不作为可上线方案 |
| 自动预热（P2-3b） | 恢复会话前先打一次 `maxTokens:1` 预热 | 不实测也不做：命中率已 99.6%，收益上界 ≈0，且可能因错峰变成净负 | **不做** |
| 输出长度压缩 | 让模型少写字省 output | PiForge 已优于对标：**668 vs 1 140 tok/调用** | 无空间 |

## 3. 结构性原因（为什么低风险杠杆都趋近于零）

**（1）cacheRead 56% 是"必须读的上下文"，不是浪费。**
模型要答对必须看到：系统提示 + 工具定义（6 640 tok 前缀）+ 历史里的决策/文件/报错。
ctx 越大，题越难，但**任何"少读"的改动都会以"答错/重读"的形式付出代价**。
L-D（−0.4%）与 L-A C2（−1.5%）都是这条规律的两个方向：一个没东西可省，一个省了就掉题。

**（2）工具输出这条路上已经没有肉。**
80 次 A/B 里 388 条工具输出：中位 **446** 字符、p75 1 541、p90 2 702、p99 4 820；
超过现有 4 000 预算的只有 **3.4%** —— 现有"4 000 字符 + 落盘指针"已经吃掉 96.6% 的输出体量。

**（3）压缩这条路被"整轮保留"的架构铁律挡住。**
真实会话最后一轮本身就有 ~22.6k tok；要压到 12k 必须拆开轮内结构（`planCompactionCut` 明确
"切点永远落在用户消息上、不劈开工具调用与结果"）。**这是架构改造，不是调参**，
而且预演已经显示"有收益的档位"与"低风险档位"之间没有可用区间。

**（4）真实请求的上下文被前缀/工具/系统提示占掉一大块（约 18k）。**
所以把"保留历史"从 33k 砍到 22k，落到整条请求上只有 −1.5%：分母太大。

## 4. L-B（会话拆分提示）为什么"不证伪但不投入"

- 它是**提示层**：上下文 ≥200k 时给"开新会话"的动作按钮（`PIFORGE_SESSION_SPLIT_HINT=1`），
  默认关闭；与任何 token 机制无关（`smoke:prefix-budget` 6 640 tok / 99.6% 不变）。
- 它的收益取决于**用户是否真的照做** —— 只能靠真实使用数据（提示出现次数、点击率、
  采纳后 7 天内 cacheRead 中位变化）判断，headless 实验测不出来。
- 因此：**代码保留、默认关闭、不投入工程预算**；若将来有多人使用的数据，再按
  `docs/optimizations/context-governance-ab.md` §6 的判据评估。

## 5. 未来重启条件（三条，缺一不重启）

1. **换模型后重跑审计**：`npm run audit:token -- --days 30`。
   换了模型=换了上下文窗口/价格/缓存语义，本节所有结论都可能失效（尤其 cacheRead 单价与
   命中率假设）。重跑后先看"cacheRead 占成本比例"与"每次调用 cacheRead 中位"是否仍同量级。
2. **会话切分 UX 立项时顺带评估**：如果将来做"会话分叉/按任务切段"的产品改造，
   顺手在同一批数据上量一次 cacheRead 中位变化 —— 那是 UX 驱动的改造，
   token 收益只是副产品，不需要单独立项。
3. **出现新的实测回归**：例如某次版本后 cacheRead/call 中位明显上升（>20%）、
   或前缀命中率跌破 95%、或出现"每轮都在全价重发"的新路径。届时按
   `docs/optimizations/token-consumption-audit.md` 的方法重新分解成本。

## 6. 口径限制（引用本文结论时必须一起带上）

- 样本 **60 个会话里 57 个在 `--D--Pi-PiForge--`（开发目录）**，且含大量 agentic 工作流、
  长工具循环；**日常短会话的成本结构可能不同**，量级不要外推。
- 审计窗口 7 天（成本拆解）/ 365 天（L-C 占比）两个口径都写在各自文档里，别混用。
- A/B 与预演的单题都是**全新会话**：单题 cacheRead 中位 8–50k，
  与"长会话中位 142 976"不是一个量级；比较只能看**相对变化**。
- 预演每格 1 次、共 24 次/轮，**不足以下显著结论**；它的用途只是"决定要不要立项"，
  本轮的用途已经用完了（不立项）。
