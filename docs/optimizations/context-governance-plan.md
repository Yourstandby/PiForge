# Token 上下文治理：立项评审（只评审，不实施）

> **口径限制（先读这段）**：本文所有数字来自 `docs/optimizations/token-consumption-audit.md`
> 的 7 天样本 —— **60 个会话里 57 个在 `--D--Pi-PiForge--` 下**，也就是"用 PiForge 开发
> PiForge"，含大量 subagent / orchestrator 运行，**偏重度 agentic**。
> 日常短会话（一问一答、很少工具）的成本结构会明显不同：单次 `cacheRead` 更小、
> output 占比更高。本文的结论方向可用，但**量级不要直接外推**到普通用户。
>
> 本文只做评审与 A/B 设计，**不实施**任何改动；`prompt-prefix.ts` / 工具域 /
> `smoke:prefix-budget` 完全不动。

## 0. 一句话结论

成本 56% 花在"每次调用都要重读的上下文"（cacheRead $12.51 / $22.36），
而缓存失效只占 5%、空闲恢复 1%。所以真正值得动的是**上下文规模**，但它同时是
"任务成功率"的命门 —— 必须先设计 A/B，用数据换结论，不能拍脑袋调阈值。

## 1. 现状基线（本轮审计，本机实测）

| 指标 | 值 |
|---|---|
| 每次调用 cacheRead | 中位 **142 976** tok · p90 471 168 · max 717 056 |
| cacheRead 成本占比 | **56%**（$12.51 / $22.36） |
| output 成本占比 | 31%（$6.83，其中 reasoning 占 output token 的 45%） |
| 未命中 input 成本占比 | 14%（$3.02） |
| 最贵 8 个会话 | 66% 成本，`avgCtx` 237k–379k tok/次 |
| 前缀失效 / 空闲恢复 | 5% / 1% |

推论：只要**每调用的上下文中位**从 143k 降到 100k，`cacheRead` 成本就近似线性降到
~70%（−≈$3.7/7 天，−16% 总成本）；但压缩会缩短模型可见历史，**可能损失任务成功率**。

## 2. 候选杠杆（4 个）

### L-A 压缩触发点前移

- **做法**：把结构化压缩（`agent-host/desktop-compaction-extension.ts`）的触发阈值
  从当前 pi/桌面默认值往下调（例如从"接近上限"提前到上限的 60–70%），
  保持现有机制不变（round 对齐 / ≤1600 tok 摘要 / 保留最近 4 轮）。
- **预估影响**：cacheRead 中位 143k → **95–110k**（压缩后语境变小，且压缩本身只发生一次）；
  单会话内压缩次数 +1~2 次。
- **对成功率的风险**：**中**。压缩会丢掉中间细节（例如 30 轮前读过的文件内容），
  模型可能要重新读一次 → 工具调用 +1，反而增加往返。
- **A/B 设计**：
  - 分组：A=现状（阈值不变）；B=阈值 60%，其余完全相同；
  - 指标：`cacheRead` 中位（主）、总成本（主）、**任务成功率**（人工判定，见 §4）、
    工具调用数/轮、压缩次数；
  - 样本量：每组 **≥20 个真实任务**（同题不同组，任务集固定），按会话随机分组；
  - 观测工具：`npm run audit:token --days N`（现在就能跑）+ 人工判定表。

### L-B 会话拆分建议（"该开新会话了"）

- **做法**：纯提示层。当会话的 `cacheRead` 中位超过阈值（如 200k）或轮数 > N 时，
  在输入框上方提示"当前会话上下文已 ~N tok，建议开新会话（可省 ~$X/轮）"，
  并提供"带着摘要开新会话"按钮（复用现有压缩摘要，不新增模型调用）。
- **预估影响**：把长会话的成本曲线**截断**；对重度使用（本样本）影响最大，
  因为 66% 成本集中在 8 个长会话。
- **成功率风险**：**低**（用户自己决定，不改变模型行为）。
- **A/B 设计**：不是"降 tok"实验，而是**可用性/采纳率实验**：
  - A=无提示；B=有提示；
  - 指标：提示出现次数、点击"开新会话"比例、**用户拒绝率**、
    采纳后 7 天内该用户 cacheRead 中位变化；
  - 样本：同一用户内部 A/B（按会话奇偶轮换），≥40 次提示机会。

### L-C subagent 上下文隔离

- **做法**：orchestrator/subagent 会话默认**不继承**父会话 transcript（只传任务描述 +
  必要上下文），避免父上下文（可能 200k+）在每个子 agent 的每次调用里被重复 cacheRead。
- **预估影响**：本样本 57/60 会话在开发目录、含大量 subagent —— 这条**可能是最大的**，
  但目前**无实测分解**（审计脚本没有按 parentSessionId 归组子会话的成本）。
  需要先补审计：把 cacheRead 按 `parentSessionId` 聚合，看子会话占多少。
- **成功率风险**：**中高**。子 agent 缺上下文会重复探查（多轮 grep/read），
  端到端可能更慢、更贵。
- **A/B 设计**：先做**观测项**（见 §5 的 P0 前置），再决定是否实验：
  - 观测：`route-heap` 同级加一个 `audit-subagent-context.mjs`，统计
    "子会话 cacheRead 总量 / 父会话 cacheRead 总量"；
  - 若占比 ≥25%，再做 A/B：A=继承（现状）/B=隔离；
  - 指标：端到端任务耗时、总 tok、成功率。

### L-D 长工具输出落盘阈值

- **做法**：`desktop-tool-output-extension` 已把超大输出落盘（`tool_history_get` 回读）。
  把落盘阈值下调（例如 8k → 4k 字符），减少每轮被 cacheRead 的 tool result 体量。
- **预估影响**：cacheRead 中位 **−5~15k**（取决于是不是 read/bash 大输出为主；
  本样本 shell 类调用占 79%，收益可能偏上限）。
- **成功率风险**：**低**（模型仍能按需回读，只是多一次工具调用）。
- **A/B 设计**：
  - A=现状阈值 / B=阈值减半；
  - 指标：cacheRead 中位（主）、`tool_history_get` 调用次数（看回读成本是否抵消）、
    成功率、端到端耗时；
  - 样本：每组 ≥20 任务。

## 3. 杠杆汇总表

| 杠杆 | 对 cacheRead 中位影响 | 成功率风险 | 实施成本 | 建议 |
|---|---|---|---|---|
| **L-D 长工具输出落盘阈值** | −5~15k（低风险、可逆） | 低 | 0.5 天 | **先做**（最安全的第一个实验） |
| **L-B 会话拆分建议** | 截断长尾（本样本 66% 成本集中） | 低（纯提示） | 1 天 | **先做**（与 L-D 并行） |
| L-A 压缩触发点前移 | 143k → 95–110k（主收益） | 中 | 1–2 天 | 第二个（需要 L-D 的 A/B 经验） |
| L-C subagent 上下文隔离 | 可能最大，**未量化** | 中高 | 2–3 天 | 先补观测再立项 |

## 4. 成功判据（硬指标）

一次干预"有效"必须**同时**满足：

1. **cacheRead 中位 ≤ 100k**（相对基线 143k，−30%）；
2. **任务成功率下降 ≤ 2 个百分点**（对照组 A 的成功率 − 实验组 B ≤ 2pp）；
3. 总成本（`audit:token` 的 `cost`）下降 ≥ 10%；
4. 端到端耗时**不劣化 >10%**（避免"省 token 但多跑几轮"）。

成功率判定方式（避免主观）：
- 固定 **20 个真实任务**（取自本仓库日常任务：改代码/查文档/修测试/写脚本四类各 5 个），
  每个任务有**可机检的完成标准**（测试通过 / 文件存在且含指定片段 / 命令输出匹配）；
- 每个任务在 A/B 两组各跑 1 次，判定由脚本自动给出 `pass/fail`；
- 成功率 = pass 数 / 20。

## 5. 建议排期（不实施，只排期）

| 阶段 | 内容 | 产出 | 前置 |
|---|---|---|---|
| P0（0.5 天） | 补观测：把 cacheRead 按 `parentSessionId` 聚合，量化 subagent 占比 | `audit-token-usage.mjs --by-session-tree` | 无 |
| P1（1.5 天） | L-D + L-B 的 A/B（两者互不影响，可同时跑） | 两个 A/B 报告 | P0 |
| P2（2 天） | L-A 压缩阈值 A/B | A/B 报告 + 是否默认开启的结论 | P1 |
| P3（按 P0 结论） | L-C subagent 隔离 | 立项或放弃 | P0 占比 ≥25% |

**门禁**：任何一项要"默认开启"，必须同时满足 §4 的四条；否则只保留设置项/提示，
不改默认行为。每一轮改动后仍要 `npm run smoke:prefix-budget` exit 0
（当前 6 640 tok / 99.6%）。

## 6. 明确不做的事

- 不动 `agent-host/prompt-prefix.ts`（前缀快照/审计/判定逻辑）；
- 不动工具域（`DOMAIN_TOOL_NAMES` / 按需域默认值）；
- 不改 `smoke:prefix-budget` 的阈值与断言；
- 不做"自动预热"（P2-3b：审计显示空闲恢复只占 1%，收益不足以抵消误判风险）。
