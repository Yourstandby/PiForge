# PiForge 0.9.x 性能优化方案（P0 / P1 / P2）

> 依据：PiForge 0.9.0 与 Pi Agent Desktop 0.4.0 的实机对比报告（冷启动 / 内存 / CPU /
> 安装体积 / token），加上本轮在本机（Windows，`D:\Pi\PiForge`，已安装 0.9.0 正在运行）
> 用新写的三个采样脚本重新取得的分项数据。
>
> 铁律约束：不破坏 `prompt-prefix.ts` 的前缀稳定性机制、latched 工具域、
> `smoke:prefix-budget`；不改 `~/.pi/agent` 语义；不新增 localhost TCP 服务。
>
> 本文档里所有数字都标注了来源命令（可复制复跑）或日志出处；**没有估算**。
> 估算一律写明"待实测"。

## 0. 汇总表

| 编号 | 优化项 | 改前（实测） | 改后目标 | 工作量 | 风险 |
|---|---|---|---|---|---|

## 2. P0（本轮已落地）

### P0-1 Host 就绪：10s 硬杀 → 20s 软超时 + 60s 硬超时

**1) 根因一句话**：`electron/main.ts` 里 `AGENT_HOST_READY_TIMEOUT_MS = 10_000`，到点直接
`child.kill()`，退出码非 0 被当异常 → `scheduleAgentHostRestart()` 退避 500ms/1s/2s… 再来一轮，
冷启动里白等 10s×2；本机 `main.log` 里累计 **197 次 `Agent Host exited {code:1}`、11 次 `{code:0}`**
（`grep -c '"message":"Agent Host exited"' main.log`）。

> 与报告的偏差（诚实记录）：本机日志里 `"timeoutMs":10000` 出现 **0 次**
> （`grep -c 'timeoutMs":10000' main.log`），说明这台机器上 0.9.0 的实际失败形态是
> **host 进程 code=1 退出**，不是超时。两种形态都归 `startAgentHost()` 的"没等到 host_ready"
> 分支，所以 P0-1 同时修两件事：超时不再杀 + UI 不再把"启动中"报成"断开"。
> code=1 的具体崩因需要单独追（见 §3.8 待办），**P0-1 不宣称修好它**。

**2) 具体改动**
- 新增 `electron/host-readiness.ts`（纯状态机，可单测）：
  - `AGENT_HOST_READY_TIMEOUT_MS = 20_000`（软）、`AGENT_HOST_HARD_TIMEOUT_MS = 60_000`（硬）；
  - `onSoftTimeout()` → `action: "report"`（**不 kill**）；`onHardTimeout()` → `"kill"`；
  - `describeHostState(state)` → `{ label, blocking }`，`degraded/booting` 明确 `blocking: false`。
- `electron/main.ts`
  - `startAgentHost()`：软超时只 `logError("Agent Host still booting after soft timeout")` +
    广播状态；再挂 `AGENT_HOST_HARD_TIMEOUT_MS - AGENT_HOST_READY_TIMEOUT_MS` 的硬超时，才 `child.kill()`；
  - 新增 `setHostReadiness()`：写 `agentHostState` 并 `webContents.send("host-state", …)`；
  - 新增 IPC `host-state:get`（渲染进程 mount 时拉一次快照，避免错过启动早期事件）。
- `app/api/health/route.ts`
  - 新增 `hostProbeState(status)`：`connecting|idle → "starting"`（旧代码把冷启动归成
    `"reconnecting"`，UI 因此显示"引擎断开，正在重连…"）。
- `hooks/useHostHealth.ts`
  - 新增 `HostEngineState = … | "starting"`；`BOOT_CONFIRM_PROBES = 3`：连续 3 次 down（≈6s）
    才允许降级成 `reconnecting/offline`；订阅 Electron `onHostState` 事件（比 3s 轮询更快）。
- `components/SystemStatusMenu.tsx`：`starting` → 冰蓝色 + "引擎启动中"（不是错误色）。

**3) 预期收益**：`app ready → host ready` 的**失败重试**从"10s + 退避 + 再一轮"变成
"0 次重试"；`app ready → 首屏可交互` 在 Host 慢/崩时**不再被拖住**（P0-2）。数字目标：
`Agent Host restart` 日志从每次启动 1–2 条降到 0；`measure:startup` 的 `host ready` 段
不再缺失（本机旧日志里该段缺失 ⇒ 首屏在等一个永远不来的信号）。

**4) 风险与回退**：挂死的 Host 会多活 40s 才被杀（内存占用多 40s，期间 UI 已可用）。
回退：把 `electron/main.ts` 里 `AGENT_HOST_HARD_TIMEOUT_MS` 临时改回 10 000 并把软超时改成
`"kill"` 分支即可（状态机保留，便于再打开）。

**5) 验收命令**
```bash
npx tsc -p electron/tsconfig.json --noEmit
node --test --test-force-exit electron/host-readiness.test.ts     # 6 pass
node --test --test-force-exit app/api/health/route.test.ts        # 含 hostProbeState 用例
npm run measure:startup        # 期望出现 "agent host ready" 段，且无 "Scheduling Agent Host restart"
```

### P0-2 启动编排：首屏只等 Next，绝不等奖擎

**1) 根因一句话**：0.9.0 的 `whenReady` 里 `await agentHostStart` 排在 `await nextReady` 之前，
Host 一旦慢（或要等满 10s 超时）就把 `showApp(port)` 也顶住 —— 首屏与引擎被串成一条链。

**2) 具体改动**（`electron/main.ts` `app.whenReady()`）
```ts
// 1. Host 最早起：只依赖 endpoint+token（同步铸出），与端口探测/建窗/Next 完全重叠
agentHostEndpoint ??= createAgentHostEndpoint();
agentHostToken ??= randomBytes(32).toString("hex");
const agentHostStart = startAgentHost();
logStartupTiming("agent host kickoff");
// 2. 建窗（startup.html 立即可见）
// 3. Next 起来后立刻加载应用 URL，Host 用 void 继续在后台就绪
void agentHostStart.then(() => logStartupTiming("agent host startup finished", { ready: agentHostReady }));
await nextReady;
await showApp(port);
```
- 渲染侧兜底：`components/ChatSurface.tsx` 会话加载自动重试从 2 次（≈4.5s）提到
  **6 次（2s/4s/6s/6s/6s/6s ≈ 28s）**，覆盖 Host 5–20s 的就绪窗口 —— 否则旧预算会在引擎
  刚起来时就先用完，用户看到的是"加载失败"。

**3) 预期收益**：`app ready → 首屏` 从"max(Next, Host)"（本机 5 567ms）变成 `Next` 单独
（本机 5 567ms，P1 后 ≈3.5s）；Host 崩/慢时首屏**不再一起挂**（实测日志里两者几乎同速，
所以收益主要体现在失败路径与 P1 之后）。

**4) 风险与回退**：首屏会在引擎没好时先显示"引擎启动中"，依赖 DB/引擎的第一批调用会 503 后
自动重试。回退：把 `void agentHostStart` 改回 `await agentHostStart`。

**5) 验收命令**
```bash
npm run measure:startup   # app ready → window 应 ≤300ms，且 host ready 段独立存在
node scripts/measure-startup.mjs --max-host-ready 10000
```

### P0-3 空闲 CPU：轮询节奏 + 背景节流 + 合成友好动画

**1) 根因一句话**：三件事叠在一起 —— ①`backgroundThrottling: false`（0.9.0 为"后台不降帧"
显式关掉），②`useWatchdogStatus` 的 `ACTIVE_MS=1000` / `IDLE_MS=4000`，
③`.tool-running` / `.context-ring-alert` 的关键帧动画 `box-shadow`+`border-color`（**每帧重绘整张卡片**）。
本机实测空闲总 CPU 52.5%，其中 renderer 18.3% + gpu 14.1%（渲染/合成侧合计 32%）。

**2) 具体改动**
| 文件 | 常量/函数 | 改法 |
|---|---|---|
| `electron/main.ts` | `webPreferences.backgroundThrottling` | `false → true`；新增 IPC `window:streaming-throttle` → `contents.setBackgroundThrottling(!enabled)` |
| `components/ChatSurface.tsx` | 新增 effect | `chat.agentRunning` 为真时 `setStreamingThrottle(true)`，结束 `false`（打字机仍需按帧） |
| `electron/preload.ts` | `syncWindowHidden()` | `visibilitychange` 时给 `<html>` 写 `data-window-hidden`；同时暴露 `setStreamingThrottle/getHostState/onHostState` |
| `app/globals.css` | `@keyframes piforge-tool-running` / `piforge-context-alert` | 只动 `opacity`/`transform`（`box-shadow` 动画改成 `::after` 叠加环），并新增 `html[data-window-hidden="true"] * { animation-play-state: paused }` |
| `hooks/useWatchdogStatus.ts` | `ACTIVE_MS/IDLE_MS/HIDDEN_MS` | `1000/4000 → 2500/10000/30000`（Host 侧卡顿阈值最矮 5s，1s 轮询没有分辨率收益） |
| `components/FileExplorer.tsx` | git status poll | `5000 → 20000` + `document.hidden` 跳过 + 切回前台立即拉一次 |
| `components/BrowserPanel.tsx` | `/api/processes` poll | `4000 → 10000` + `document.hidden` 跳过 |
| `components/AgentRailPanel.tsx` | 秒表 tick | 只在**有 running agent** 时启动，`document.hidden` 时跳过 |
| `components/SubagentPanel.tsx` | 秒表 / fallback | 同样加 `document.hidden` 跳过 |

**3) 预期收益**（改前 → 改后目标，单核口径，可见窗口、无会话运行、采样 8s）
- renderer：18.3% → **≤3%**；gpu：14.1% → **≤6%**（合成友好动画 + 托盘暂停）；
- 总 CPU：52.5% → **≤15%**（agent-host 那段另算，见 P0-4）；
- 窗口在托盘时：总 CPU → **≈0**（`backgroundThrottling: true` + `animation-play-state: paused`）。

**4) 风险与回退**
- 风险 A：流式时若 `setStreamingThrottle(true)` 没生效（preload 旧版本），后台会"囤字"。
  回退：`webPreferences.backgroundThrottling` 改回 `false`（一行）。
- 风险 B：watchdog 从 1s 变 2.5s，"卡住"提示最多晚 1.5s 出现。回退：只把 `ACTIVE_MS` 调回 1000。
- 风险 C：`.tool-running` 视觉从"外发光"变成"描边呼吸"。回退：`git revert` 该 CSS 块。

**5) 验收命令**
```bash
npm run lint && npx tsc --noEmit
npm run measure:idle        # 断言总 CPU ≤10%，打印每进程明细
node scripts/measure-app-processes.mjs --seconds 8 --json   # 归档对比
```
采样口径（新增说明，避免"空闲"定义不一致）：窗口保持可见并聚焦、无会话在跑、无工具执行、
不移动鼠标，采样 8s。

### P0-4 浏览器桥心跳与轮询（本轮新发现，非报告项）

**1) 根因一句话**：`electron/browser-host-bridge.ts` 只处理 `hello_ok` 与 `res`，**没有回 `ping`**
→ Host 侧 `HEARTBEAT_TIMEOUT_MS = 60_000` 到点断开 → 桥 1s 后重连 → 永远循环。
本机 `main.log` 里 **1 351 次 `heartbeat timeout`**，稳定每 **61.4s** 一次
（`grep -o '"time":"[^"]*"[^}]*heartbeat timeout' main.log | tail -3` → 09:20:41 / 09:21:42）。
叠加 `browser.poll` 恒 700ms（面板没打开也在轮），对应 agent-host 空闲 12.0% CPU。

**2) 具体改动**（`electron/browser-host-bridge.ts`）
```ts
if (frame.kind === "ping" && typeof frame.nonce === "number") {
  socket.write(`${JSON.stringify({ kind: "pong", nonce: frame.nonce })}\n`);
  continue;
}
// 轮询节奏：面板可见 700ms，不可见 3s
private pollDelayMs(): number {
  if (this.options.pollMs) return this.options.pollMs;
  return this.options.getManager()?.getState?.().visible ? 700 : 3_000;
}
```
新增回归用例 `electron/browser-host-bridge.test.ts`：喂 `{kind:"ping",nonce:7}` 必须回
`{kind:"pong",nonce:7}`；非数字 nonce / 未知帧不得崩、不得误回。

**3) 预期收益**：`heartbeat timeout` 从 1 351 次（每 61s 一次）→ **0**；
agent-host 空闲 CPU 12.0% → 目标 **≤4%**（少一份重连 + 少 1.4 次/s 的 RPC）。

**4) 风险与回退**：心跳写入失败时可能掩盖断链 —— 现有 `handleClose` 靠 socket 的
`close/error` 事件仍能触发重连；回退：删掉 ping 分支即可恢复旧行为（旧行为本身就是 bug）。

**5) 验收命令**
```bash
node --test --test-force-exit electron/browser-host-bridge.test.ts   # 3 pass
# 让应用跑 5 分钟后再看日志里是否还有心跳超时
python - <<'EOF'

log=r"C:\Users\Luo Wei\AppData\Roaming\piforge\logs\main.log"
tail=open(log,'rb').read()[-2_000_000:].decode('utf8','replace')
print("heartbeat timeout:", tail.count("heartbeat timeout"))
EOF
```

## 3. P1（架构级，收益最大）

### P1-4 拆掉 `127.0.0.1:30141` + Next standalone，回到"零内部端口"

**1) 根因一句话**：渲染进程的所有数据都要经过 `next start`（standalone `server.js`，本机
471.7 MB RSS、5 567ms 就绪、安装多 290 MB），而这个"服务"对本机单用户桌面应用没有任何必要
—— 架构铁律里本就写着"Host 与 Next 只走命名管道 / Unix Socket"。

**2) 具体改动（分 4 步，每步独立可回滚）**

**Step A · 渲染侧传输抽象（不改后端）**
- 新增 `lib/api-transport.ts`：
  ```ts
  export async function apiFetch(path: string, init?: RequestInit): Promise<Response> {
    const bridge = (window as any).electronAPI?.api;
    if (bridge?.request && typeof window !== "undefined" && window.location.protocol === "piforge:") {
      return bridge.request(path, init);        // → ipcRenderer.invoke("api:request", …)
    }
    return fetch(path, init);                    // 浏览器开发模式保持原样
  }
  export function apiStream(path: string, init?: RequestInit): EventSourceLike { … }
  ```
- 把 **93 处 `fetch("/api/…")`（43 个文件）** 与 **17 处 `new EventSource("/api/…")`** 机械替换为
  `apiFetch` / `apiStream`。这一步之后 Next 仍可服务，功能零变化，可先合。

**Step B · Host 侧补齐 RPC（70 条路由 → Host 方法）**
- 分类迁移（`app/api/**/route.ts` 共 70 条、3 822 行）：
  | 类别 | 条数（估） | 去处 |
  |---|---|---|
  | 纯 Host 代理（health / watchdog / processes / sessions / fleet / herdr / mcp / memory / orchestrator / subagents / tool-outputs / extensions / trust / skills …） | ~35 | Host `contract/methods.ts` 新增方法名，`server.ts` 的 `case` 表加分支（多数是 1:1 转发，函数体照抄） |
  | 本地 IO + Host 授权（files / file-index / git status·diff·commit / statusline / default-cwd / select-directory / projects） | ~20 | 直接搬进 `agent-host/`（`lib/host-files.ts` 的授权调用已在那儿：Host 内不再需要 `files.authorize` 往返） |
  | SSE / 事件（agent events、processes、terminal、subagents、fleet、config） | ~15 | 复用已有 `GlobalTopic`；`agent.event` 走 `ipcRenderer` 推送（`server.ts` 的 `agent.event` 已按 sessionId 分发） |
- 单测随迁：`app/api/**/route.test.ts` 里的纯逻辑断言改为对 Host 的 case 表 / 纯函数断言，
  保留 `scripts/` 下的 smoke。

**Step C · 静态直出（`output: "export"` + 自定义协议）**

### P2-6 把按需域扩到 memory / orchestrator

**1) 根因一句话**：`DEFAULT_ON_DEMAND_DOMAINS = ["shell"]`（`lib/domain-tools.ts`），
memory + orchestrator 仍常驻，两者合计 623 tok/轮。

**2) 具体改动（若开启）**：`lib/domain-tools.ts` 的 `DEFAULT_ON_DEMAND_DOMAINS` 加
`"memory", "orchestrator"`；设置项 `onDemandDomains` 与 `PIFORGE_ON_DEMAND_DOMAINS`
语义不变（已经是"环境变量 > 设置项 > 默认值"）；`smoke:prefix-budget` 增加一条
"三域都按需"的预算用例。

**3) 实测收益（本机，`measure-prefix --mode host --turns 4`）**
```
默认（shell 按需）                              前缀 6 640 tok
PIFORGE_ON_DEMAND_DOMAINS=shell,memory,orchestrator   前缀 5 992 tok   → −648 tok/轮
```
**但本方案建议：不默认开启。** 理由（不是估算，是既有 A/B + 本次实测的组合）：
- 收益 −648 tok/轮 > 300 tok 门槛，**但代价是每个域第一次使用时多 1 次 `tool_search` 往返 +
  一次前缀全量重写**（该轮历史全部按未缓存计费）。项目内第 5 步的 30 轮实测结论是
  "激活两轮多烧 ≈21k 未缓存 token，29 轮稳态才省回 ≈18k"；本次前缀只降到 5 992 tok，
  break-even 仍在 30 轮量级 —— 与"每 call 增量 668 tok"的量级相比不值得，且违反了
  P2 的硬约束"不得为省 token 牺牲工具发现的正确性"（多一次往返就是多一次失败面）。
- 具体收益/成本模型（可复算）：`省 648 × N 轮` vs `激活成本 ≈ 当时历史总量 × 1 次`。
  一个 20k 历史的长会话，激活一次就要 20k ⇒ break-even ≈ 31 轮；100 轮才划算。
- **保留开关**：设置页加一行说明"长会话（>100 轮）或不支持前缀缓存的模型可开启"。
  这条结论写进 `lib/domain-tools.ts` 的注释与 README，避免下次又被"省 648 tok"诱惑。

**4) 风险**：激活尖峰回退（历史上真出现过 7.8k–14.5k 尖峰）。**已在代码里加回归用例**
（`agent-host/on-demand-domains.test.ts`）：三域都按需时，每次激活**只允许 +1 个工具名、
不允许撤销已激活的域、同一激活集合序稳定** —— 满足它前缀最多重写一次。

**5) 验收命令**

### P2-8 空闲恢复前按成本决定"预热 or 提示"

**1) 根因一句话**：`agent-host/cache-warming.ts` 只在会话**创建/恢复**时
`warmPromptPrefix()` 无条件预热（`maxTokens: 1` 重放）；长历史下这次预热本身就要全量输入，
而"缓存已过期 + 历史很大"时应该先算成本再决定（或直接提示用户）。

**2) 具体改动**
- `cache-warming.ts` 新增纯函数
  ```ts
  export function decidePrewarm(input: { historyTokens: number; prefixedTokens: number; hitRate: number; priceRatio?: number }):
    { action: "prewarm" | "prompt" | "skip"; reason: string };
  ```
  规则：`historyTokens >= PREWARM_MAX_TOKENS(80_000)` → `"prompt"`（先问用户）；
  `hitRate >= 0.9 && historyTokens < 4_000` → `"skip"`（预热不值得）；
  其余 → `"prewarm"`。
- `rpc-manager.ts` 调用点（`setBinding` 里 `warmPromptPrefix` 之前）先跑 `decidePrewarm`；
  `"prompt"` 时通过 `ExtensionUiBridge` 发一个非阻塞 `notify`（不是 `confirm`，避免卡住会话）。
- `agent.state` 暴露 `prewarm: { action, reason, historyTokens }` 供状态栏显示。

**3) 预期收益**：避免"恢复一个 20 万 token 会话时先白付一次 20 万输入"；可量化：
该场景请求数 −1、input tokens −history。

**4) 风险**：判断错误导致本该预热却没预热（下一次真正的请求仍是全价）。
缓解：默认阈值保守（只在 ≥80k 历史时改成提示）；纯函数 + 单测覆盖三档。

**5) 验收命令**
```bash

PIFORGE_DEBUG_CACHE=1 npm run dev:electron   # 日志出现 "[cache] prewarm sent/skipped <reason>"
```
