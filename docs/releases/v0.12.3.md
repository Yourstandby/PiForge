# PiForge v0.12.3 — no more "waiting for the first token", and sending actually reacts

**English** · [简体中文](./v0.12.3.zh-CN.md)

Released: 2026-11-25

The previous public version was v0.12.2. There are no new switches in this release: a recurring event-stream hang is pulled out at the root, messages are no longer dropped silently, and the Pi core moves to 1.6.0.

## Highlights

### Stuck at "waiting for the first token" — only a refresh showed anything; now it heals in 12 seconds

Symptom: you send a message and the UI sits at "PiForge is thinking… / waiting for the first token…" without moving; refresh manually and the whole answer that had just been produced is there, intact. It happened repeatedly, and only a refresh helped.

The root cause is a **delivery watermark mismatch**. The host's `lastDeliveredSeq` means "delivered to any subscription", while the Next-side subscription hub is removed the instant the browser cancels the SSE — but `agent.subscribe` had already been issued at that moment, leaving an **orphan subscription nobody consumes**: it keeps eating every event frame and drives the watermark up to a position the browser never received. The next resume starts after that watermark, so that segment is lost for good and only a refresh (reloading the transcript from disk) makes it visible.

Three fixes:

- **No more orphan subscriptions**: the hub identity is verified before and after creating the subscription, and if it has already been removed `agent.unsubscribe` runs immediately; `close()` deletes only its own mapping, so concurrency cannot wipe out a newly created hub.
- **Resume counts what actually reached a listener**: a hub-independent `agentListenerSeq` is added and used for resume when there is no explicit `fromSeq`, no longer blindly trusting the host watermark.
- **Recovery when stuck**: a new 12s rule for "not a single real event received this round" (a real-increment timestamp that excludes `connect()`'s reconnect bookkeeping) triggers an automatic reconnect (carrying the browser's real watermark, so the host resumes the missed segment from its buffer) plus a reload of the round's output from disk; 15s cooldown, at most 4 attempts per round. Rounds already inside streaming / a tool turn keep the 120s long threshold, so long tools are left alone.

### Sending actually reacts: no more silent drops

- Hitting "the host is still running" no longer returns immediately: it goes down the queue path (visible / editable / immediately sendable), and when the host really is idle a new round starts at once.
- The send gate expires on its own (8s), so one lost event can no longer wedge it forever.
- Failures stay visible: the bubble is marked "not delivered", and a persistent reason plus retry / dismiss sits above the input.
- The host no longer rejects messages while reloading resources (concurrent reloads reuse the same in-flight promise).

### Pi core upgraded to 1.6.0

All three packages (`pi-ai` / `pi-coding-agent` / `pi-mcp`) are pinned to exactly 1.6.0. PiForge itself needs zero code changes (upstream is imported through the single `sdk-adapter.ts` seam).

Upstream behavior changes to be aware of:

- The default model of `openai` / `azure` / `openai-codex` becomes GPT-6.2 Sol (same price).
- The `find` path pattern is now relative to the searched directory (`src/*.ts` no longer matches `pkg/src/a.ts`; cross-level matches need `**/src/*.ts`).
- The two GPT-6.2 tiers do not accept reasoning effort `none` / `minimal`, so "thinking level off" is unavailable on those two models.

## Behavior changes (please note)

- A stuck event stream no longer needs a manual refresh or a stop click: it recovers within 12s (reconnect + content from disk).
- Pressing send while running queues the message, and a bubble the host rejected carries the "not delivered" mark (behavior from v0.12.2 is unchanged).
- The default models, the `find` matching rule and the thinking-level ceiling change with upstream 1.6.0, see above.

## Install notes

The three installers are still unsigned, as in v0.12.2:

- **Windows**: SmartScreen will block it; choose "More info → Run anyway".
- **macOS**: Gatekeeper will block it; right-click → Open, or run `xattr -dr com.apple.quarantine`.
- **Linux**: the `.deb` is unsigned and needs `sudo dpkg -i`.
