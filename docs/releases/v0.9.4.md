# PiForge v0.9.4

**English** · [简体中文](./v0.9.4.zh-CN.md)

Released: per the CI output of tag `v0.9.4` (Windows NSIS + ZIP, Linux deb, macOS universal).

> **Why 0.9.4 exists**: the `v0.9.3` tag ran `desktop-packages.yml`; Windows / Linux passed, but macOS hung at the end of packaging in `smoke-packaged-standalone`, inside `smoke-extension-ui-bridge.mjs`'s `timed out waiting for a frame`. 0.9.3 produced no Release, so this version = everything in 0.9.3 + this smoke / pipeline fix, with **no functional difference from 0.9.3 at the code level** (the old tag is not rewritten; the semantic version simply moves forward one).

## Theme one: fixing a false red in the release pipeline

`smoke-extension-ui-bridge.mjs` used to report only `timed out waiting for a frame`, with no clue where it hung, and the per-frame budget was hard-coded at 20 s. A macOS runner's cold start (APFS plus reading tens of thousands of `node_modules` files for the first time) is several times slower than local, so one **normal but slow** startup was judged as a host deadlock.

Changes (`scripts/smoke-extension-ui-bridge.mjs`):

- Per-frame wait 20 s → 60 s by default, overridable with `PIFORGE_SMOKE_UI_TIMEOUT_MS` / `PIFORGE_SMOKE_TIMEOUT_MS` (matching the existing convention in `smoke-packaged-static.mjs`).
- `waitFor` becomes **queue matching**: frames that do not match are no longer discarded. The old "take a frame → test the predicate → drop it on mismatch" swallowed an `extension_ui_request` that arrived while waiting for the `agent.subscribe` reply, so waiting for it later was guaranteed to time out — a real bug in the script itself, not merely a budget problem.
- Timeout messages carry a phase label plus the most recently received frame types: `timed out waiting for agent.create response after 60000ms; recent frames: res#1, evt:session_state`.
- Every phase is logged (`host ready` / `handshake ok` / `agent.create ok` / `agent.subscribe ok` / `extension_ui_request received` / `marker confirmed`), with the host's last 15 output lines attached on failure.
- Timeout failures are retried once automatically (`PIFORGE_SMOKE_UI_ATTEMPTS`, default 2).
- `scripts/smoke-packaged-standalone.mjs` prints `UI bridge smoke took <ms>`, so CI can tell "hung" from "slow but passing" at a glance.

`.github/workflows/desktop-packages.yml`:

- Top-level `PIFORGE_SMOKE_UI_TIMEOUT_MS: "180000"` (CI gives 3× headroom).
- When the macOS packaged smoke fails, an extra step re-runs the same smoke with the Agent Host compiled from the repo: passing means the problem was in the packaged artifact (layout / symlinks / dependency resolution), failing again means an environment timing problem.

## Theme two: call compaction (same content as 0.9.3)

**Fewer round trips for the same task**. No tools removed, no capability reduced — only the number of model round trips and the share of output spent thinking are compressed:

- codemode is on by default and defaults to `only` (ordinary tools are no longer declared to the model but called in one batch by a script; the settings page "extensions and MCP → Codemode" switches back to "declare tools as usual").
- The prompt gains four static batching / budget constants (batching first, quote before re-testing, call budget, read the whole traceback before changing code).
- Truncation continuation guidance becomes "read it in one codemode script batch / page with `tool_history_get`".
- The host writes `defaultThinkingLevel: "low"` on first start (only when the key is missing, atomically, changeable in the settings page).

Plus what 0.9.3 already contained — night mode, thinking streamed live, message timestamps, questions from before compaction visible, image scaling in packaged builds — see [`v0.9.3.md`](./v0.9.3.md) and [`CHANGELOG.md`](../../CHANGELOG.md).

## Artifacts

Installers / deb / dmg are built by `desktop-packages.yml` in CI after the `v0.9.4` tag is pushed (NSIS + ZIP + `latest.yml` + deb + macOS universal dmg/zip + `SHA256SUMS.txt`); nothing is built locally.

## Migration and upgrade

- Upgrading from 0.9.3 needs no migration (0.9.3 produced no Release, so upgrading straight from 0.9.2 is fine too): sessions and settings live in `~/.pi` and `%APPDATA%\piforge` respectively.
- The first start writes one `defaultThinkingLevel: "low"` line (only when missing, once).
- New sessions go through codemode by default; if you do not want the batching layer, turn it off in the settings and tools are called directly again.
