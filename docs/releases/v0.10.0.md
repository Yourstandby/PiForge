# PiForge v0.10.0

**English** · [简体中文](./v0.10.0.zh-CN.md)

Released: per the CI output of tag `v0.10.0` (Windows NSIS + ZIP, Linux deb, macOS universal).

Theme of this release: **boundaries tightened**. "Clicked and nothing happened / clicked and had to wait" is removed one by one across branches, the queue, the watchdog and the file sidebar; the host side gains a tool execution scheduler and a hard shell timeout guard, so "a big job next door makes even a simple task here stall" no longer happens. The three default-behavior changes (tool timeouts, per-batch parallelism, exploration order) are called out separately below.

## Branches: see all of them, carry conclusions away, no dead clicks

- **The branch dropdown uses the complete branch graph**: the session API's `tree` only contains the current path, so sibling forks are missing from it, and the old implementation's `hasBranch()` was always false — hence the frequent "it says there is no branch even though I forked". It now builds a tree from `getBranches`'s nodes, and clicking a row switches to that node's leafId.
- **Multi-root branch graphs get a virtual root** (`lib/session-branches-view.ts`): a pi `.jsonl` can end up with a multi-root structure from manual edits or cross-device merges, which the renderer takes as "the current session has no branches". Multiple roots are now merged into a virtual root before deciding branching.
- **Switching branches can distill the branch you leave** (a switch in the branch dropdown, **off by default**, remembered in localStorage): when enabled, switching goes through `navigateTree(target, { summarize: true })`, compressing the branch you leave into one `branch_summary` appended to the target node. When exploring two approaches you no longer have to splice both conversations into the context (splicing breaks the prefix cache), and no conclusions are lost. A cold session (no live session in the process) cannot be summarized and returns `summarySkipped: "not-live"`, which the UI explains.
- **Forking and branching are disabled while running**: the host already refuses to fork during streaming (the `.jsonl` may be appended to) and to switch branches (it would move the live session's leaf), but the old frontend only logged it to the console — pressing the button did nothing. The buttons are now disabled with a "possible once this round finishes…" hint, and a failure pops a Chinese reason instead of staying silent.

## Queued messages: deletable, reorderable

- A delete button is added to queued messages (red on hover), and the host dequeues by revision: the frontend updates optimistically and refetches the queue on a revision conflict, so neither "deleted but still there" nor "deleted the wrong one" happens.

## Watchdog

- **Intervention gets an immediate receipt**: `agent.intervene` now accepts synchronously and calls `result()` right away, while the real delivery runs in the background. The button no longer waits for the current tool to finish, and the latency of a steer landing at a turn boundary is no longer part of the UI's wait chain.
- **Long commands are really interrupted**: on a forced skip, if a tool has already run more than 10 s, `abortBash()` runs first and then the intervention is delivered; short commands are not interrupted, so results are not thrown away for nothing.
- **Only the genuinely stuck line is marked**: the watchdog state is session-level, and the old implementation judged by "the whole turn is running with no result", so tool rows that had finished long ago inside the same message were also painted red with a red timer. The tool call id now runs through `TurnBlock → ToolCallCard`, and only rows matched by `stuckToolCallIds` go red.
- **`verdict` stays backward compatible**: when an older host has no `verdict`, the verdict bar is not rendered, so no hollow panel appears.

## The file sidebar no longer queues behind tools

File authorization (`files.authorize`) now uses its **own RPC connection** (`lib/host-files.ts` creates one and hangs it on `globalThis.__piforgeFilesHostClient`). The old implementation shared the main connection with agent events, and a single socket's write queue is FIFO — once tool output piled up, a file-click authorization request was pushed past the 15 s timeout, showing up as "clicking a file does nothing while tools run". With two connections, 40 interleaved RPCs all passed in measurement; this constraint is now written into the pitfalls section of `AGENTS.md` — do not change it back to the main singleton.

## Host: tool execution scheduler (on by default)

When one session in a host process fires 25 parallel tools, all their shell output is absorbed on one event loop, and ordinary requests from other sessions can only queue. New `agent-host/desktop-tool-scheduler-extension.ts`, which **only delays execution — it never changes arguments or results**:

- Two gates: global heavy 4 / light 12, per-session heavy 2 / light 6; heavy is classified by command characteristics.
- It uses the SDK's `emitToolCall` to await each handler and a per-call `_beforeToolCall`, so an over-quota call queues inside its own `tool_call` hook.
- When no slot arrives within 60 s it gives up on queuing and runs normally — better to overshoot occasionally than to wedge work with the scheduler.
- Release happens at `tool_result`; there is also a 15 min forced reclamation (so an approval block or a dead call cannot leak a slot), and `session_shutdown` clears everything that session holds.
- Only after queuing more than 1.5 s is a hint appended to that call's result; normal results are untouched, character for character.
- It registers after the approval extension: a call blocked by approval must not hold a slot first.
- `codemode` / `tool_search` / nested calls are exempt (they are already batched by nature).

## Hard shell timeout guard (on by default, **default behavior changed**)

pi's `bash` / `powershell` `timeout` is optional with no default, so a model that omits it never times out. Measurement showed one long-lived call in a batch of 25 hanging the whole batch for 300 s. New `agent-host/desktop-tool-guard-extension.ts`:

- At the `tool_call` stage it fills in `event.input.timeout` on the spot: 120 s for ordinary commands, 900 s for heavy ones, with caps of 600 s / 900 s.
- Invalid values (`'300'` / `0` / `NaN`) are corrected to the default instead of letting pi throw.
- When a batch runs more than 8 in parallel, a suggestion is appended to the result of the first over-limit call only (once per batch, no blocking, no lost work).
- Only when the error itself is `timeout:<seconds>` is a "how to change it" sentence appended, with the original body kept intact.

**Impact**: long tasks that do not pass `timeout` explicitly (long-lived processes, benchmarks, full packaging) are interrupted at 120 s (900 s for heavy ones). Pass `timeout` explicitly for longer runs, or adjust `PIFORGE_TOOL_TIMEOUT_SECONDS` / `PIFORGE_TOOL_TIMEOUT_HEAVY_SECONDS` / `PIFORGE_TOOL_TIMEOUT_MAX_SECONDS`, and turn it off entirely with `PIFORGE_TOOL_GUARD=0`.

## Prompt: batching budget tightened one more notch

- `BATCHING_RULES` gains "at most 8 parallel in one batch" and "run heavy commands separately with an explicit `timeout`".
- Exploration becomes **`rg -l` first for file names, then a targeted `read`** (folded into existing item 1, so no extra line).
- Still a pure static constant with no interpolation, one prefix (+26 characters), cache-safe.

## Measurement tooling

- `npm run measure:prefix -- --summary` prints only the ≤10 lines needed to decide (one line of turns/sys/tools/prefix/body per runtime, plus whether the prefix is stable, the delta between the two runtimes, the cache hit rate and the prefix audit); the full report is still `--json` / `--dump`.

## Upgrade notes

- Tray / auto-update: the usual `electron-updater` chain (check → download → restart to install after the task ends).
- The installers are not code-signed; SmartScreen on Windows and Gatekeeper on macOS will warn, which is expected.
- The Linux `.deb` updates through `DebUpdater`, which needs root authorization to install; integrity is verified by the SHA512 in `latest-linux.yml`.

## Fix: the packaged host loaded no user extensions

Since v0.9.2 the packaged build prefers the single-file host bundle (`agent-host/bundle/host.mjs`, cold start 3.1 s → 0.7 s). But esbuild did not declare the `PI_BUNDLED_NODE` constant the Pi SDK depends on, so the SDK thought it was running in an **unbundled dist tree** and computed aliases from `import.meta.url` (which is the bundle itself once packaged) to import `~/.pi/agent/extensions/*`, with failures swallowed into a session-level error.

Symptom: the host was ready, every RPC worked, sessions could be created and subscribed, but **not one of the user's own extensions took effect** (no `session_start` hook, no `ctx.ui.*` dialogs, custom tools and commands gone). Every packaged build from v0.9.2 through v0.10.0 was in this state; unbundled `npm run dev` / `npm run dev:electron` were unaffected.

Fix and guards:

- `scripts/bundle-agent-host.mjs` gains `define: { PI_BUNDLED_NODE: "true" }`, taking the SDK's preset embedded path (`jiti/static` + virtual modules). Bundle size 15.3 MB → 14.6 MB.
- New `npm run smoke:extension-ui-bundled`: reproduces the packaged layout (wrapper `index.js` → `./host.mjs`) and runs the Extension UI Bridge smoke, going red immediately if the define is removed. Wired into CI.
- `npm run dist` / `npm run pack` now also run `smoke-packaged-standalone`. Previously only macOS's `dist:mac` ran it, which is why the same bug stayed green on the Windows / Linux pipelines.

## Baseline content (upstream pi-agent-desktop v0.10.0 → v0.11.0)

This repository's baseline is upstream `pi-agent-desktop@v0.11.0`, and PiForge does not ship a 0.11.0 of its own. The upstream v0.10.0 / v0.11.0 notes are merged here (the former `docs/releases/v0.11.0.md` was folded into this file), with the version number still following PiForge's own 0.10.0.

### Upgrade (upstream v0.10.0, 2026-10-12)

- **Pi SDK upgraded to 1.1.0**: `@earendil-works/pi-ai`, `pi-coding-agent` and `pi-mcp` move from 0.99.1 across major versions to 1.1.0. Passing through 1.0.0 / 1.0.x / 1.1.0 brings a codemode prompt about 40% cheaper in tokens, codemode image generation, project-level MCP overrides, `pi.registerToolRenderer()`, a fully cancellable MCP OAuth chain with request timeouts, tool execution duration `durationMs`, Claude Haiku 5.5 and other upstream improvements.
- **Vulnerability fixes land with upstream**: 1.1.0 pins `brace-expansion@5.0.12`, fixing GHSA-q2hr-2g5m-vwhr and the other advisories flagged upstream.

### Fixes (upstream v0.10.0)

- **Azure provider rename adaptation**: upstream 1.0.3 changed the provider id from `azure-openai-responses` to `azure`, and the Azure entry's icon key in the model configuration UI follows. Existing configurations need manual migration: the provider key in `auth.json` and `models.json.providers`, plus `defaultProvider` in `settings.json`, the provider patterns in `enabledModels` and the provider/model keys in `modelThinkingLevels` all move to `azure`. The API id `azure-openai-responses` and the `AZURE_OPENAI_*` environment variables are unchanged; restoring an old Azure session may fall back to another model, and the original prompt cache cannot be reused, so confirm the current model before continuing.
- **MCP credential boundary**: a project `mcp.json` is refused when it references model provider credentials directly; global `auth.provider` must use HTTPS (only loopback HTTP is exempt). The check runs on both load and save.
- **MCP project override**: when a project only changes `enabled`, `exposure` or `toolExposure`, the global connection and authentication configuration are preserved; the configuration UI and the runtime use the same merged result, and the native `/mcp` keeps the override file's source.
- Editing a project override preserves global authentication and the inheritance of later connection updates; a rejected configuration still shows its error state and can be corrected or deleted.

### Security dependency updates (upstream v0.10.0)

- Next.js and eslint-config-next update to 16.3.8, Sharp to 0.35.5, and the fixed releases of http-cache-semantics and source-map-js are refreshed.
- The transitive dependency KaTeX is unified at 0.18.2, so old dependency ranges cannot keep installing affected versions.
- Dependency audit for upstream v0.11.0: 5 high, 8 moderate, 0 critical — pre-existing ESLint and Electron packaging toolchain warnings; no cross-major downgrades or forced dependency upgrades were made.

### Sidebar update (upstream v0.11.0, 2026-10-16)

- **Folder-style project navigation**: projects render as collapsible folders, making session ownership and fork hierarchy clearer; row spacing, selection state, hover actions and the explorer area are refined.
- **Three project sort orders**: name (natural) by default, switchable from the top sort menu to "recently active" or "manual". Recently active orders by the newest session time within each project.
- **Drag to reorder projects**: drag project folders up and down to change the order; dropping switches to manual sort automatically and saves it. Long lists support edge auto-scroll, and dragging pauses while searching. Dragging only changes display order — it does not move directories on disk, nor change the order of sessions inside a project or their fork ownership.
- **More coherent interaction animation**: folder expand/collapse, drag preview, list displacement and drop feedback are all refined; keyboard reordering and Escape to cancel are supported, and the system "reduce motion" setting is respected.
- The Chinese and English UI copy is synchronized, and the sort menu keeps exactly three options: name, recently active and manual.

### Fixes (upstream v0.11.0)

- When renaming or deleting a session fails, the specific error returned by the server is shown; a missing or invalid response falls back to a generic error message.

### Compatibility and known limitations (upstream)

- Upstream v0.10.0 is a cross-1.0 major upgrade and, beyond the Azure icon, also adapts to the new MCP authentication and project override rules. Type checking alone cannot prove runtime compatibility; the relevant boundaries were verified with isolated configurations and real-SDK regression tests. See [docs/research/pi-core-upgrade-2026-10-11.md](../research/pi-core-upgrade-2026-10-11.md).
- Running alongside the terminal CLI still shares the `~/.pi/agent` directory; concurrent writes to the same session from both ends are still unsupported.
- Related upstream change: [sidebar and sorting PR #60](https://github.com/Chasen-Liao/pi-agent-desktop/pull/60).
